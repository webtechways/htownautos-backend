Builds on [[identity-sync-b1-b4]] and [[identity-sync-b2]]. Design doc: `docs/identity/CLERK-SYNC-DESIGN.md`.

## Controller (`apps/api/src/clerk-webhooks/clerk-webhooks.controller.ts`)
- After svix verification: `prisma.clerkWebhookEvent.createMany({data:[{id: svixId, type, payload}], skipDuplicates:true})` — Prisma's `createMany + skipDuplicates` IS Postgres `ON CONFLICT DO NOTHING`, no raw SQL needed. Only publish `identity.clerk.events {eventId}` when `result.count > 0`. `svixId` comes from the raw `svix-id` request header (lowercased by Express), NOT `event.data.id` (that's the Clerk resource id, a different thing).
- **Deliberately left the existing `organization.*`/`organizationMembership.*` inline handling untouched and synchronous** (not moved behind the queue) — it does real multi-step work (tenant creation, role resolution, Clerk org metadata patch via `require('@clerk/backend')` inline) that isn't a trivial move. `ClerkEventsConsumer` ADDS behavior on top (recompute userType + refresh metadata) for `organizationMembership.*`, consuming the same event row after the inline handler already ran synchronously in the same request.
- Constructor now takes `(PrismaService, RabbitMQService)` — `RabbitMQModule` is `@Global()` so no module import needed (`clerk-webhooks.module.ts` only imports `PrismaModule`).

## Consumer (`apps/data-sync/src/identity/clerk-events.consumer.ts`)
- `processEvent(eventId)` re-reads `ClerkWebhookEvent` fresh every time; `row.processedAt` truthy → no-op (redelivery-safe). On success sets `processedAt`; on failure increments `attempts`+`error` and **leaves `processedAt` null** — a poison event (`attempts >= MAX_CLERK_EVENT_ATTEMPTS = 8`) is simply excluded from the sweep's `WHERE processedAt IS NULL AND attempts < 8`, never falsely marked processed.
- `clerk-events-sweep.service.ts` — same 5-min cron + `2^attempts` (cap 240min) backoff shape as B2's `IdentitySyncSweepService`, but keyed on `ClerkWebhookEvent.createdAt` (no `updatedAt` column on that table).
- **`user.created` matching order**: `clerkUserId` exact (redelivery) → `external_id` (= our own `User.id`, set when B2's push *created* this Clerk user) → verified primary email (case-insensitive). Any match whose `clerkUserId` is already set to a DIFFERENT Clerk id is a conflict — skip linking, log a warning, never overwrite a live link. Only verified email/phone (`verification.status === 'verified'`) are trusted; unverified Clerk identifiers are ignored.
- **Schema gap found**: `User.email String @unique` is NOT NULL — a phone-only (SMS-code) Clerk sign-up has no email at all. Worked around with a synthetic placeholder `${clerkUserId}@clerk.no-email.htownautos.internal` on create. Flag to lead-architect before B5/production Clerk migration if SMS-only signups become common — the schema should probably make `email` nullable.
- **`user.updated` loop guard**: builds the *incoming* `DesiredClerkState` (same shape as B2's push, shared via `clerk-desired-state.ts`) using webhook fields merged onto current DB values, hashes it, and compares to `User.clerkSyncHash`. Equal hash = this event is just an echo of our own last B2 push → only `clerkEventAt` is bumped (ordering guard stays current), no other write, **no push is ever enqueued from this path at all** (handleUserUpdated never calls `rabbitMQ.publish`). Different hash = apply: email/phone/name/avatar → User; names always cascade to every linked Buyer; Buyer.email/phone (contact fields) only follow if they still equalled the OLD login value (case-insensitive compare before the User row is overwritten).
- **`user.deleted`**: `clerkUserId = null`, `clerkSyncStatus = SKIPPED`, `clerkSyncError = 'clerk_user_deleted'`, `clerkSyncHash = null`. Buyers are never touched.
- **`organizationMembership.*`**: calls `recomputeUserType` then unconditionally `rabbitMQ.publish(CLERK_PUSH_QUEUE, {userId})` to refresh Clerk `publicMetadata`. This relies on the STAFF safety fix below — do not enqueue this without it.
- **Buyer creation for web sign-up** (`unsafe_metadata.signupSource === 'web'`): `Buyer.dateOfBirth`/`currentAddress`/`currentCity`/`currentState`/`currentZipCode` are all required non-null columns with no data available from a Clerk sign-up — filled with explicit placeholders (`dateOfBirth: 1900-01-01`, address fields `''`) and a `notes` string marking the lead incomplete for staff follow-up. `Buyer.phoneMain` has `@@unique([tenantId, phoneMain])` — using `''` for every phone-less signup WOULD collide on the second one; used `` `pending-${userId}` `` instead (per-user-unique, clearly non-phone-shaped placeholder). `Buyer.source = 'web-signup'` (the `source String?` column already existed in the schema, contrary to what an earlier read of the design doc might suggest — verify before assuming a field needs adding).
- Idempotent buyer creation: pre-checks `Buyer.findFirst({userId, tenantId: PORTAL_TENANT_ID})` before create — a redelivered `user.created` never creates a second lead or double-notifies.

## Safety fix in B2's `IdentityClerkPushConsumer` (`identity-clerk-push.consumer.ts`)
**Found and fixed a real ban-staff bug while wiring B3's `organizationMembership.*` → push.** `pushUser`'s original logic: `portalBuyers.length === 0` → `banIfLinked` (bans in Clerk). That branch is trivially true for EVERY staff member (they never have a portal Buyer) — so enqueuing a push after any org-membership change (routine: invitation accepted, role changed) would have banned them. Added a guard: `if (user.userType === 'STAFF') { refreshStaffMetadata(...); return; }` before the ban branch — new `refreshStaffMetadata` method updates Clerk `publicMetadata` only (via `updateUserMetadata`), never bans. This is a deliberate deviation from a literal reading of the B3 brief's "enqueue a push to refresh metadata" instruction — implementing it literally would have been a production-breaking regression for all 7 existing staff users. Always sanity-check a design doc's literal instruction against what the downstream consumer it invokes actually does before wiring a new caller to it.

## Shared hash module (`apps/data-sync/src/identity/clerk-desired-state.ts`)
Extracted `DesiredClerkState` interface + `hashDesiredState()` out of the B2 push consumer (was private/inline there) so B3's consumer can compute an IDENTICAL hash for its loop-guard comparison — the two must never drift or the loop guard silently breaks. Both files import from here now.

## Testing pattern for a module that imports `@htownautos/auth`
Importing ANY named export from `@htownautos/auth`'s index pulls in `guards/customer.guard.ts`'s module-scope `createClerkClient({secretKey: process.env.CLERK_SECRET_KEY!})` side effect (see [[global-guard-di-crashloop]]) — even if the file under test only uses `recomputeUserType`/`PORTAL_TENANT_ID`. Always `jest.mock('@htownautos/auth', () => ({...}))` wholesale in the spec (provide a hand-rolled `recomputeUserType` mock that replicates the real count+update logic against the test's own prisma mock, plus a `PORTAL_TENANT_ID` string) rather than trying to partially mock or use `requireActual`.
