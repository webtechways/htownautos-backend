Context: htownautos-backend `feat/social-suite`, package B5/"B3 Inbox" (`apps/api/src/inbox/**`, `apps/api/src/social/webhooks/**`, `libs/social/src/messaging/**`, Twilio/SMS changes, `apps/data-sync/src/social/inbox-jobs/**`). Builds on [[social-suite-b2-patterns]] and [[social-suite-b3-patterns]].

## Root jest config had NO `moduleNameMapper` for `@htownautos/*` — any spec importing a lib via its alias failed to resolve
`package.json`'s `"jest"` block (already fixed for `rootDir`/ts-jest per [[jest-and-tsc-verification]]) had no `moduleNameMapper`, so any spec file whose import chain touches `@htownautos/social`, `@htownautos/common`, etc. (not just relative imports within the same lib) fails with "Cannot find module '@htownautos/X'" — ts-jest doesn't read `tsconfig.base.json`'s `paths` on its own. Fixed by adding an explicit `moduleNameMapper` mirroring `tsconfig.base.json`'s `compilerOptions.paths` 1:1 (each entry is a *specific* regex `^@htownautos/name$` → its `index.ts`, not a single generic `@htownautos/(.*)` regex — several packages map to `apps/ai-services/src/...`/`apps/image-service/src/...`, not `libs/`, so a generic libs-only regex would break those). Existing specs (`libs/social/src/publish/*.spec.ts`, `apps/data-sync/src/social/publisher/*.spec.ts`) never hit this because they only import relative sibling files, never their own package's `@htownautos/social` alias.

## `moduleFileExtensions: ["js","json","ts"]` silently shadows edited `.ts` files with STALE checked-in `.js`/`.d.ts` siblings
This repo has compiled `.js`/`.d.ts`/`.js.map` files sitting *next to* their `.ts` source in `apps/api/src/**` (e.g. `apps/api/src/twilio/twilio-webhook.controller.js` alongside `.ts` — looks like an old build's output got committed into `src/` by mistake, not a Nx convention). With `js` listed before `ts` in `moduleFileExtensions`, Jest resolves the STALE `.js` version instead of the `.ts` file you just edited — a method you just added shows up as "not a function" in the test with no compile error anywhere (ts-jest never even touches the file, since module resolution picked the `.js` sibling before transform). Symptom: `TypeError: controller.someNewMethod is not a function` when the method visibly exists in the `.ts` source. Fixed by reordering to `["ts","js","json"]` in `package.json`'s jest config — verified no regression against all 4 pre-existing `.spec.ts` files after the change. **Whenever a jest test can't see a method/behavior you just added to a `.ts` file, check for a stale `.js` sibling in the same directory before debugging further** — `ls apps/api/src/<dir>/*.js` next to the `.ts` you're testing.

## Meta webhook needs the RAW body for `X-Hub-Signature-256` — same carve-out pattern as Stripe/Shippo
`apps/api/src/main.ts` already special-cased `bodyParser.raw` for `/api/v1/stripe/webhooks` and `/api/v1/shippo/webhooks` (HMAC needs the exact bytes, not a re-serialized `JSON.stringify(req.body)`). Added `/api/v1/social/webhooks/meta` to that same branch. The controller then does `req.body as Buffer`, verifies `X-Hub-Signature-256` against it, and only then `JSON.parse`s it manually — never trust Nest's automatic body parsing for a signed webhook.

## Twilio SMS webhook signature validation existed as a dead method for ~this entire build
`TwilioService.validateWebhookSignature(signature, url, params)` (uses the `twilio` npm SDK's `validateRequest`) was written but never called from `TwilioWebhookController` — the `@Headers('x-twilio-signature')` param was captured and silently ignored on both `sms/incoming/:tenantId/:phoneId` and its `/status` sibling. Wired it up via a new private `assertValidTwilioSignature(req, signature)` that reconstructs the exact webhook URL from `PUBLIC_API_URL` (falling back to `x-forwarded-*`) + `req.originalUrl` (strip query string), throws `ForbiddenException` (403) on mismatch, and short-circuits entirely when `TWILIO_VALIDATE_SIGNATURE=false`. Twilio signs the exact URL it was configured to POST to — must match `TwilioService`'s own `buildWebhookUrl()` construction (`${base}/api/v1/twilio/sms/incoming/:tenantId/:phoneId[/status]`) byte-for-byte, including scheme/host.

## `SmsMessage.mediaUrls`/`InboxMessage.attachments` store S3 **keys**, not URLs — resolved to signed URLs only at response time
Per the brief's "keep keys" instruction: MMS media (needs Twilio Basic Auth to fetch) and WhatsApp Cloud media (needs a Graph access token to fetch) are downloaded server-side and copied into the private bucket via `S3Service.uploadBuffer(buf, folder, ext, mimeType)`, and only the returned `.key` is persisted — never a signed URL (those expire; persisting one bakes in a TTL bug). `InboxMessage.attachments` JSON internal shape is `{kind, key, mimeType, name}` (see `apps/api/src/inbox/inbox-mappers.ts`'s `StoredAttachment`), converted to the contract's `{kind, url, mimeType, name}` only inside `toInboxMessageView`, via `MediaResolverService.signedUrl(key)`, on every read. Messenger/Instagram/X/Bluesky DM attachments are the one exception: their URLs come straight from the platform's own CDN (already fetchable, no auth needed to render) and are stored pass-through as `{kind, url, mimeType, name}` (no `key`) — `toInboxMessageView` checks `a.key ? signedUrl(a.key) : a.url` to handle both shapes in one function.

## `assignedToId` translation: DB column is `TenantUser.id`, wire contract is `User.id` — translate at BOTH read and write, never store the wrong one
`InboxConversation.assignedToId` (FK to `TenantUser`) vs. contract's `assignedTo.id`/request `assignedToId` (`UserSummary.id`, i.e. `User.id`). Write path (`InboxService.updateConversation`): resolve the incoming `User.id` to a `TenantUser.id` via `prisma.tenantUser.findFirst({where:{tenantId, userId}})` — 404 if not found (cross-tenant `assignedToId` must never silently no-op or write a raw `User.id` into the FK column, which would 500 on the FK constraint or silently corrupt the relation). Read path: reuses `apps/api/src/social/posts/mappers.ts`'s `toUserSummary(tenantUser)` (already does the `tenantUser.user.id` translation) — do NOT re-derive this mapping locally, it's the one function both B2b (posts) and B5 (inbox) share for this exact shape.

## `InboxConversation.senderKey` MUST be consistent across every write path for the same conversation, or you silently fork the thread
`senderKey` (`@@unique([tenantId, channel, senderKey, contactExternalId])`) is whatever denormalized id identifies "us" on that channel — `TwilioPhoneNumber.id` for SMS/WhatsApp-via-Twilio, `SocialAccount.id` for every social channel. Every one of `SmsService.sendSms`/`handleIncomingSms`/`handleSmsStatusUpdate`/`sendForInbox` must derive `senderKey` the *same* way for the same logical thread, or `SocialIngestService.upsertConversation` (which matches on the unique key) silently creates a SECOND conversation instead of continuing the first — no error, just a fork nobody notices until support asks "where did my reply go." Concretely: `handleSmsStatusUpdate` does NOT try to reconstruct `channel`/`senderKey` from the `SmsMessage` row (risk: guessing wrong on an SMS vs. WhatsApp-via-Twilio row that share the same Twilio number) — it looks up the InboxMessage already created for that `smsMessageId` and reuses ITS `channel`/`conversation.senderKey`/`conversation.contactExternalId` verbatim. Prefer "read back what you already wrote" over "recompute and hope it matches" whenever a status/update callback needs to rejoin an existing thread.

## `SocialIngestService.recordInboxMessage` unconditionally overwrites `body`/`attachments` on every upsert — status-only webhook events must preserve them manually
`recordInboxMessage` (frozen, B1-owned) does `messageData = {..., body: input.body ?? null, attachments: input.attachments ?? [], ...}` and always applies it via `update` when the row already exists (idempotent by `smsMessageId` or `(channel, externalId)`). A WhatsApp delivery/read status webhook has no body/attachments of its own — if you naively call `recordInboxMessage` with `body: null` for a status event, it WIPES the original message text on every delivery receipt. Fix used in `MetaWebhookService.handleWhatsAppStatus`: look up the existing `InboxMessage` by `(channel, externalId)` first, and pass its existing `body`/`attachments` straight through unchanged. Same risk applies to any future status-only mirror path (X DM read receipts, etc.) — always read-before-write when the update carries no real content.

## DM pollers (X/Bluesky/Mastodon) have no dedicated cursor column — re-fetch last N events per poll instead
`SocialAccount` has no free column for "last DM cursor" per platform (and `lastSyncAt` is presumably going to be claimed by the B4 comment-poller for the SAME accounts — a real collision risk flagged in the report, not resolved). `DmPollService` (`apps/data-sync/src/social/inbox-jobs/dm-poll.service.ts`) instead just re-fetches the most recent ~20 DM events/conversations every 2 min and relies on `recordInboxMessage`'s idempotency `(channel, externalId)` to no-op duplicates — correct but not incremental; fine at this volume, revisit if a tenant has high DM volume across many accounts. Uses `account.lastErrorAt`/`lastErrorMsg` (existing columns) to log X's 403 (free-tier DM API lockout) only once per distinct error message instead of every 2-minute tick.

## `@nestjs/schedule`'s `CronExpression` has no `EVERY_2_MINUTES`
Only 1/5/10/30/45-minute (and hour+) presets exist. Use a raw cron string `'*/2 * * * *'` with `@Cron('*/2 * * * *')` instead of reaching for a `CronExpression` member that doesn't exist (compiles fine as a plain string; TS only complains if you try a nonexistent `CronExpression.X`).
