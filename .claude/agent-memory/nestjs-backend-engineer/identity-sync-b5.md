## Running `PrismaService`/`ensureUserForBuyer` outside Nest DI (in a script)
`ensureUserForBuyer(prisma: PrismaService, ...)` is typed against the class `PrismaService`, not a structural shape — `PrismaService` has `private prisma`/`private pool` fields, so a raw `new PrismaClient({adapter})` is NOT assignable to it (TS treats classes with private members as nominal). A script that needs to call it must do `const prismaService = new PrismaService(); await prismaService.onModuleInit();` (constructor already sets up the pool+client eagerly; `onModuleInit` just does `$connect()`) — exactly like Nest would, just manually. `scripts/backfill-customer-identity.ts` does this alongside its own separate raw `PrismaClient` (two pools/connections in one script — fine for a one-off, documented as a judgment call in the handback).

## Clerk read-only lookups in a script vs Clerk writes
`scripts/backfill-customer-identity.ts` does read-only `clerk.users.getUserList`/`getUser` lookups directly (batches of 10, 200ms pause between batches) to CLASSIFY each buyer (`link`/`create`/`skip`/`conflict` — pure function `decideClerkAction`, unit tested) — but never calls a Clerk *write* endpoint. In `--apply` it only sets `User.clerkSyncStatus=PENDING` + publishes `identity.clerk.push`; the existing B2 consumer does the actual Clerk write later (it has its own rate limiting/retry/password-safety). Same batching helper reused for the stale-link 404 sweep (`users.clerkUserId`/`buyers.clerk_user_id` that 404 in Clerk — found 3+1 in the original audit).

## Synthetic no-email Clerk address must never be pushed back to Clerk
Found and fixed a real bug while doing the B5 data-quality cleanup: B3's `handleUserCreated` mints `${clerkUserId}@clerk.no-email.htownautos.internal` for phone-only sign-ups (schema: `User.email NOT NULL @unique`), then immediately calls `stampSyncedHash` so the INITIAL hash already reflects that placeholder — so the sweep alone was NOT the risk (no spurious first push). The real risk: if that User's `Buyer` ever gets touched again (`ensureUserForBuyer`'s "already linked" branch unconditionally sets `clerkSyncStatus=PENDING`) and something else in the desired state changes (name, phone), `identity-clerk-push.consumer.ts`'s `updateLinkedUser` would unconditionally call `ensurePrimaryEmail(clerkUserId, placeholderEmail)` — writing the garbage `@clerk.no-email...` address as a NEW Clerk email and setting it primary, silently breaking the customer's real login email. Fixed in `identity-clerk-push.consumer.ts`: `isSyntheticClerkEmail()` (from `@htownautos/common`, new `libs/common/src/utils/incomplete-profile.utils.ts`) guards `ensurePrimaryEmail` in `updateLinkedUser`, the `emailAddress` array in `linkOrCreateUser`'s `createUser` call, and the email branch of `findByIdentifier`. Always trace a "mint a placeholder to satisfy a NOT NULL column" pattern forward through every consumer that later reads that column, not just the one that wrote it.

## Placeholder masking (new `libs/common/src/utils/incomplete-profile.utils.ts`)
Shared constants/helpers so the B3 writer (`clerk-events.consumer.ts` `createWebSignupBuyer` — `phoneMain: pending-<userId>`, `dateOfBirth: 1900-01-01`, `currentAddress/City/State/ZipCode: ''`) and every reader agree on one definition: `isPendingPlaceholderPhone`, `isPlaceholderDateOfBirth`, `isPlaceholderAddressField`, `isSyntheticClerkEmail`. Applied in two mappers (found by tracing `BUYER_INCLUDE`/`findOne` in `buyers.service.ts` and `BUYER_SAFE_SELECT` in `portal.service.ts` — there is no single shared "BuyerMapper", CRM staff and portal customer each have their own):
- `apps/api/src/buyers/entities/buyer.entity.ts` (`BuyerEntity` constructor, staff-facing) — masks to `null` via `(this as any)` cast (declared field types are non-nullable `string`/`Date` per the Prisma schema; the cast is the same pattern already used there for Decimal-to-number conversion).
- `apps/api/src/portal/portal.service.ts` (`BUYER_SAFE_SELECT` + new `maskIncompleteProfilePlaceholders()`, applied in both `getProfile` and `updateProfile`'s return — NOT in the `ensureUserForBuyer` call inside `updateProfile`, which must keep receiving the real just-submitted values).
- Also added `Buyer.metaValue = { incompleteProfile: true }` on creation in `createWebSignupBuyer` (no schema change — `metaValue Json?` already existed) as an explicit machine-readable marker alongside the placeholder fields.
- Audited User.email exposure for the "never shown in UI" requirement: `BUYER_INCLUDE` (buyers.service.ts) does NOT include the `user` relation at all today, so `User.email` (and thus the synthetic placeholder) isn't currently surfaced through any buyer/portal endpoint — no additional masking needed there, just don't add a `user: {select:{email:true}}` to `BUYER_INCLUDE` without adding this same masking.

## Scripts added
`scripts/backfill-customer-identity.ts` (`decideClerkAction` pure function + spec, `--dry-run`/`--apply`/`--tenant <id>`) and `scripts/reprocess-clerk-events.ts` (`--dry-run`/`--apply`, republishes `clerk_webhook_events` with `processedAt IS NULL AND attempts < 8` to `identity.clerk.events`). Both wired as `npm run identity:backfill` / `identity:reprocess` (→ `ts-node scripts/<file>.ts`, extra flags need `-- --apply` through npm). Neither was executed against a real DB/Clerk per house rules — CI/CD runs them with the user's approval.
